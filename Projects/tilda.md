### Как читать витрину сайта (для независимой сверки)
Статические страницы = кэш, врут; наружу отдаёт только фид:
`https://store.tildaapi.com/api/getproductslist/?storepartuid=<uid>&recid=<recid>&c=<любое>&getparts=true&getoptions=true&slice=1&size=300`
Пары `recid`/`storepartuid` — в HTML страницы категории (`recid:'…',storepart:'…'`; всего
по сайту 39 блоков). Пустой `storepartuid` не работает, списка категорий фид не отдаёт.
Полный список страниц — из `https://elnaturelshop.ru/sitemap.xml` (13 шт.), НЕ по ссылкам
с главной (так теряется `/sale`). В ответе у товара есть `externalid` — наш ключ.
⚠️ Выводы делать только когда ВСЕ запросы прошли: один упавший дал ошибочное «10 товаров нет
на сайте» вместо 2.

### Ключ сопоставления
**Tilda External ID = `_` + YClients `good_id`.** Совпал у всех 500 товаров → без дублей.
SKU в Тильде пуст — по артикулу матчить НЕЛЬЗЯ.

**Ozon `offer_id` — тот же ключ `_<good_id>`** (переведено 30.07.2026, 274 из 276 карточек:
«Прочее» 7, Tangle Teezer 68, Moroccanoil 94, Invisibobble 105). Два товара не сопоставлены
по решению Ирины: «Браслет Чан-Лу» (нет в YClients, удаляет из Ozon) и «Набор разноцветных
резинок с фигурками 10 шт» (товара нет, висит остатком). Дубликатов нет, каждый артикул
проверен по каталогу YClients. Смена — `POST /v1/product/update/offer-id`, ≤25 за раз;
после каждой партии перечитывать карточки: артикул встал И название не изменилось.
Связь с Яндекс.Маркетом не заводили.

⚠️ **Метод сопоставления по названиям** (пригодится при новых товарах). Обе стороны привести
к нижнему регистру, ё→е, **свести кириллические двойники латиницы** (`асеорхукмтвн`→`aceopxykmtbh`
— в названиях Ozon буквы перепутаны), отделить цифры от букв («250мл»=«250 мл»), русские слова
длиннее 5 букв обрезать до основы («заколки»=«заколка»). Мера Жаккара **со взвешиванием
редких слов** (IDF) — иначе название модели тонет среди общих «резинка для волос».
Раздавать кандидатов **глобально, один товар YClients — одной карточке Ozon** (жадно по
убыванию схожести): без этого две похожие карточки забирают один товар.
На этих правилах все 161 позиции второго этапа сошлись автоматически, спорных — 5.
- ⚠️ Категория **«Магазин»** в YClients = товары под маркетплейс (10 шт., 9 из них Moroccanoil
  мелких форматов 10–20 мл). Давать им перевес, но ТОЛЬКО когда кандидат и так почти лучший:
  безусловный приоритет притягивает чужое («CURL Control мусс 150 мл» → «FRIZZ CONTROL спрей 20 мл»).
- ⚠️ Ловушки, на которых ошибались: один оттенок в двух объёмах (200/30 мл), одна модель в
  трёх размерах (спрей 160/50/20 мл), «True Black» у пяти линеек сразу, похожие имена наборов
  (Petit Four / Petit Bijoux). Проверка на дубликаты артикулов ловит такое надёжнее сходства.

### Поток A: YClients → Тильда (остатки + цены)
- `GET /goods/{company}` (постранично) → остаток из `actual_amounts` по складу `for_sale`,
  цена `cost`. Заливка фидом **CommerceML** (`import.xml` + `offers.xml`), HTTP Basic.
- Остаток — **абсолютным числом, не разницей**: сверка встроена, ошибка не копится.
- Расписание: **5 мин** — изменения по складу; **каждый час** — полная сверка всех 500;
  раз в месяц — чистка журнала. Отдельного ночного прогона нет.
- Изменения ловим сравнением списка складских операций (`TX_SEEN`, окно 3 суток):
  появившиеся И исчезнувшие номера — исчезнувший = операцию удалили (`changed_after`
  у YClients НЕ работает). Ловится ЛЮБОЕ движение, не только продажи.
  ⚠️ **Изменение ЦЕНЫ движения не создаёт** → его видит только полная сверка (потому ежечасная).
- **Новые карточки Тильда создаёт сама** («создавать новые» ВКЛ) — название и цена из YClients,
  External ID проставляется, без категории; Ирина дозаполняет.
- **Названия и артикулы НЕ синхронизируем** — соответствующие галки в Тильде ВЫКЛ
  (проверено: прогон 500 товаров исправил 14 цен и не тронул ни одного названия).

### Поток B: Тильда → YClients (заказ с сайта → списание)
- Вебхук корзины (галки «товары массивом» + «externalid») → `doPost` → ОДИН
  `POST /storage_operations/operation` со всеми позициями (атомарно), **`type_id=1` продажа,
  `cost=0`** → финансовая операция НЕ создаётся (подтверждено на боевом), выручку Ирина
  проводит статьёй дохода. Функция `createOnlineSale_`.
- **Подпись** «Заказ из интернет-магазина El'Naturel Shop №<номер>» — двумя PUT после создания
  (позиции + документ). Не прошёл PUT → лист «Очередь повторов»; склад при этом уже верный.
  ⚠️ **Номер ведём САМИ** (`ORDER_SEQ_NEXT`, засеян 233): Тильда «порядковый номер заявки»
  в вебхук не передаёт — только внутренний `orderid`, `systranid` всегда 0. При расхождении см. [порядок работы со счётчиком](https://github.com/irinkadirinkad-lgtm/tilda-yclients-integracia-magazin/blob/main/.claude/skills/my-skill-proverka-integracii/SKILL.md#0а-счётчик-заказов-order_seq_next).
- Идемпотентность по `tranid`; лист несопоставленных для товаров без пары.
- ⚠️ **Подпись и нулевая цена — признак канала для ФИНАНСОВ** (связь двух проектов, 26.07.2026).
  Финансовая интеграция отличает продажу с сайта от магазинной так: цена позиции 0 → читает
  комментарий документа → ищет слова «интернет-магазин». Менять текст подписи или начать писать
  реальную цену — только вместе с финансовой интеграцией, иначе каналы перестанут разделяться.

### Нагрузка и лимиты (замерено 26.07)
- **YClients: 5 запросов в СЕКУНДУ** (официально). Мы делаем ≈650 в сутки, Тильда ≈200.
  Apps Script: 20 000 внешних запросов/сутки (у нас ~3%), 90 мин триггеров/сутки (~22 мин).
- ⚠️ Опасен не суточный объём, а ПИК. Реальные объёмы: заказ 1–10 позиций, ПРИХОД накладной
  10–150. Четыре уровня: (1) при >20 изменившихся товаров читаем постраничным каталогом
  (~8 запросов независимо от количества, `fetchGoodsSmart_`); (2) `ycPace_` — минимум 250 мс
  между обращениями (≤4 запроса/с); (3) `LockService` — пятиминутка и полная сверка никогда
  не идут параллельно; (4) повтор при 429 (3/9/20 с), у Тильды 10/20/30 с.
  5xx повторяем только для чтения — повтор POST продажи мог бы её задвоить.
  `doPost` замка не ждёт: Тильде нужен быстрый ответ.

### Грабли (проверено на боевом — не повторять)
- **Цена** применяется ТОЛЬКО с блоком `<ПакетПредложений>`+`<ТипыЦен>`. Без них ответ
  «success», а цена не меняется.
- ⚠️ **ВЕБХУК ТИЛЬДЫ АКТИВИРУЕТСЯ ТОЛЬКО ПРИ СОХРАНЕНИИ** и лишь если приёмник ответил 200
  за 5 секунд на проверочный `test=test`. Не успел — вебхук в списке есть, но не срабатывает
  НИКОГДА (потеряли полдня). Отвечать на `test=test` мгновенно, до таблиц/почты/API;
  после правок, влияющих на скорость, — ПЕРЕСОЗДАТЬ вебхук (пересохранения не хватило).
  Диагностика «дошло ли»: счётчики в `?action=master`; сравнить с Email/Telegram-приёмщиками
  того же блока — получили они заказ или нет.
- ⚠️ **Формат вебхука — form-urlencoded с КВАДРАТНЫМИ СКОБКАМИ** (`payment[products][0][…]`),
  `[quantity]` — количество, **`[amount]` — СУММА** (ловушка), `[systranid]` всегда 0.
- ⚠️ **YClients игнорирует `comment` при создании операции** — только отдельным PUT
  (документу нужны `type_id`, `storage_id`, `create_date` с полным временем; позиции — полное
  тело). `PATCH` — 405. **`GET /storages/transactions` комментарий позиции ВСЕГДА отдаёт
  пустым** — читать `GET /storage_operations/operation/{company}/{doc}`.
- ⚠️ **У CommerceML Тильды есть лимит частоты** («Many requests») → партии по 250, пауза 8 с,
  повтор `checkauth` 10/20/30 с.
- ⚠️ **У токена нет прав удалять складские документы** (405/403) — только руками Ирины.
- Вебхуков на склад у YClients НЕТ → только polling. Публичный API Тильды read-only,
  товары — только через CommerceML.

### Отмена заказа

Отменой заказа Ирина занимается вручную. Удаление заказа в Тильде само по себе
не возвращает остаток в YClients. Возврат проводят в YClients по складской операции
«Продажа товара» с номером заявки, с предварительной сверкой по общим правилам.
Тильда получит актуальный остаток при следующей синхронизации, обычно до 5 минут.
Автоматизацию возврата Ирина отложила 25.07.2026.
